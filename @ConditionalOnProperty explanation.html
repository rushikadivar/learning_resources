✅ 1. How does @ConditionalOnProperty work internally?

@ConditionalOnProperty is a conditional annotation used to include or exclude bean definitions based on the presence and value of a property in the application's environment (typically application.properties or application.yml).

🔍 Internal working:

  • It is a meta-annotation on top of @Conditional(…Condition.class), specifically it uses:

    java
    @Conditional(OnPropertyCondition.class)

  • When the Spring container processes configuration classes, it evaluates this condition during the bean definition phase.

  • The OnPropertyCondition checks for:

    • Property existence.

    • Its value (if specified).

    • Prefix + name(s).

  • If the condition is satisfied, the annotated bean/class gets registered; otherwise, it is skipped.

🔧 Code breakdown:

java
@Configuration
public class MyConfig {
  
  @Bean
  @ConditionalOnProperty(name = "feature.x.enabled", havingValue = "true", matchIfMissing = false)
  public MyService myService() {
      return new MyService();
  }
}

  • If feature.x.enabled=true, then MyService is registered.

  • If the property is missing or set to false, the bean will not be created.

✅ 2. What are the phase and components involved (minor details)

🔄 Lifecycle phase: Bean Definition Phase

  • Happens before any beans are instantiated.

  • During @Configuration class processing, Spring evaluates Condition interfaces.

✅ What does @Component do?

The @Component annotation marks a class as a Spring-managed bean. It tells Spring:

"Register this class as a bean in the application context during component scanning."

✅ Annotations that Internally Contain @Component

These are specialized stereotype annotations provided by Spring, all of which are meta-annotated with @Component:

AnnotationPurposeMeta-annotated with @Component
@ComponentGeneric component — the base stereotype✔️ Yes
@ServiceMarks a class as a service layer component✔️ Yes
@RepositoryMarks a class as a data access layer component✔️ Yes
@ControllerMarks a class as a web controller in Spring MVC✔️ Yes
@RestControllerSpecialized version of @Controller that returns data (not views)✔️ Yes (via @Controller)

🧠 How does it work internally?

Here’s how @Service is defined under the hood:

java
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Component
public @interface Service {
    String value() default "";
}

Similarly, @Repository and @Controller are also defined like this.

That means these annotations inherit all the behavior of @Component, including:

  • Being detected during component scanning

  • Being instantiated and managed by the Spring container

  • Supporting dependency injection via @Autowired, constructor injection, etc.

🔁 @RestController is a little special:

java
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Controller
@ResponseBody
public @interface RestController {
}

So technically, @RestController → @Controller → @Component.

✅ Clarifying Their Roles

AnnotationPurpose
@ComponentMarks a class to be registered as a Spring bean during component scanning
@EnableAutoConfigurationTells Spring Boot to automatically configure beans based on classpath, properties, etc.

They both register beans, but the mechanism is entirely different:

🔧 How @Component Works

  • Spring scans packages (usually starting from the package where your main class is) for classes annotated with:

    • @Component

    • @Service

    • @Repository

    • @Controller

  • These beans are registered in the ApplicationContext.

🔁 Controlled by @ComponentScan (which is included in @SpringBootApplication).

🔧 How @EnableAutoConfiguration Works

  • Uses the spring.factories (or META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports in recent Spring Boot versions) to:

    • Find classes annotated with @Configuration

    • Automatically create and configure beans based on:

      • Classpath presence (e.g., Tomcat, HikariCP)

      • Configuration properties

      • Conditional annotations like @ConditionalOnClass, @ConditionalOnProperty

This is runtime logic — no component scanning is involved.

📦 Example:

Ah, great — you're diving into Spring's prototype scope, which has some subtle but critical behavior that developers often misunderstand.

✅ Question:

If a bean is defined with prototype scope, are its dependencies (properties) also injected as new instances?

❌ Short Answer:

No, not automatically.

When you define a bean as @Scope("prototype"), only that bean itself is created as a new instance every time it is requested.
But — any dependencies it has (injected via @Autowired) are not necessarily prototype unless explicitly configured so.

🧠 Let’s unpack it with an example:

java
@Component
@Scope("prototype")
public class OrderService {
    
    @Autowired
    private PaymentProcessor paymentProcessor;
}

Now suppose:

java
@Component
@Scope("prototype")
public class PaymentProcessor {
    // ...
}

Now here's the key behavior:

What happensExplanation
Requesting OrderService multiple times via applicationContext.getBean(OrderService.class)✅ You get a new instance each time.
But does paymentProcessor inside it also get recreated each time?❌ Not by default. It may be shared, depending on how it's injected.

🔬 Why?

Spring injects dependencies once at the time of bean creation, and by default, singleton beans inject singleton dependencies.

Even for prototype beans, Spring resolves all dependencies only once when the bean is created, so if a prototype bean is injected into a singleton, it won’t behave like a prototype anymore.

🔁 Real Example: Singleton consuming a Prototype

java
@Component
public class InvoiceService {

    @Autowired
    private OrderService orderService; // prototype-scoped
}

Even though OrderService is @Scope("prototype"), InvoiceService is a singleton.
➡️ Spring creates OrderService only once at startup, injects it, and that same instance is reused forever.

✅ How to truly get new prototype instances at runtime?

Use one of the following techniques:

✅ 1. ObjectFactory<T> or Provider<T> (Recommended)

java
@Component
public class InvoiceService {

    @Autowired
    private ObjectFactory<OrderService> orderServiceFactory;

    public void generateInvoice() {
        OrderService orderService = orderServiceFactory.getObject(); // 🔄 New instance each time
    }
}

Or with javax.inject.Provider:

java
@Autowired
private Provider<OrderService> orderServiceProvider;

✅ 2. Lookup method injection (less common now)

java
@Component
public abstract class InvoiceService {

    public void generateInvoice() {
        OrderService orderService = getOrderService(); // gets new prototype
    }

    @Lookup
    protected abstract OrderService getOrderService();
}

ConceptBehavior
@Scope("prototype") on a beanNew instance on each .getBean() call

Inject prototype into singleton directly❌ Only created once (not true prototype behavior)

Excellent question — this dives right into how Spring handles constructor vs. field injection, especially when a class has multiple constructors and mixed injection styles.

🔍 Question:

What happens if a class has:

  • A no-arg (default) constructor

  • A parameterized constructor

  • Field-level injection (@Autowired on fields)

✅ Spring's Constructor Resolution Rules

When Spring creates a bean, it follows a constructor resolution algorithm to decide which constructor to use.

🧠 Here's the priority order:

  1. Single constructor only?

    • Spring uses it (even if it's parameterized).

    • No @Autowired needed.

  2. Multiple constructors?

    • Spring looks for one with @Autowired

    • If only one is annotated, it uses that.

  3. No constructor is annotated?

    • Spring picks the default (no-arg) constructor.

    • Then injects fields and setters after construction.

  4. Multiple constructors annotated with @Autowired?

    • ❌ Spring throws an exception due to ambiguity.

✅ Field Injection vs Constructor

Let’s see what happens with this kind of setup:

java
@Component
public class UserService {

    private final UserRepository userRepository;

    @Autowired
    private PaymentService paymentService;

    public UserService() {
        System.out.println("Default constructor");
        this.userRepository = null;
    }

    public UserService(UserRepository userRepository) {
        System.out.println("Parameterized constructor");
        this.userRepository = userRepository;
    }

    public void serve() {
        userRepository.doSomething();
        paymentService.pay();
    }
}

❓Which constructor will Spring use?

  • Since there are two constructors and none are annotated with @Autowired:
    ✅ Spring will choose the default constructor

    • It will still inject paymentService via field injection

    • But userRepository will be null, which could cause an NPE

✅ Best Practices

PracticeWhy
✔️ Use constructor injectionEncourages immutability, easier to test, mandatory dependencies are obvious
✔️ Use @Autowired on constructor if multiple existRemoves ambiguity
❌ Avoid mixing constructor + field injection in the same classLeads to unclear lifecycle and harder debugging
❌ Avoid relying on default constructor unless necessaryForces use of field injection and makes dependencies implicit

✅ Correct Version (Preferred)

java
@Component
public class UserService {

    private final UserRepository userRepository;
    private final PaymentService paymentService;

    @Autowired  // optional in modern Spring (if only one constructor)
    public UserService(UserRepository userRepository, PaymentService paymentService) {
        this.userRepository = userRepository;
        this.paymentService = paymentService;
    }
}

  • 💡 Spring will automatically pick this constructor

  • Dependencies are injected immediately

  • Encourages testability and clarity

✅ Summary

ScenarioBehavior
Only one constructor (any type)Used automatically (even if parameterized)
Multiple constructors, one with @AutowiredThat one is used
Multiple constructors, none with @AutowiredSpring uses the default constructor and then does field injection
Multiple constructors with @Autowired❌ Exception (ambiguity)
Field injection usedWorks, but less preferred and delayed (post-construction)
