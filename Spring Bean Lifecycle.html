🔁 Spring Bean Lifecycle – Full Explanation

Spring Bean Lifecycle refers to the series of steps that a bean (an object managed by Spring container) goes through from instantiation to destruction.

Spring provides many hooks to interact with the bean at different lifecycle stages.

🔍 Lifecycle Phases Overview

PhaseDescription
1. Bean InstantiationSpring creates a new instance of the bean using constructor or factory method
2. Populate Properties (Dependency Injection)Dependencies are injected via fields, setters, or constructors
3. Bean Name AwareIf the bean implements BeanNameAware, Spring injects the bean name
4. Bean Factory AwareIf the bean implements BeanFactoryAware, Spring injects BeanFactory reference
5. Application Context AwareInjects ApplicationContext if bean implements ApplicationContextAware
6. Pre-initialization (BeanPostProcessor#postProcessBeforeInitialization)All registered BeanPostProcessor run before initialization
7. InitializingBean / Custom Init MethodCustom initialization logic is executed (afterPropertiesSet() or @PostConstruct)
8. Post-initialization (BeanPostProcessor#postProcessAfterInitialization)Post-processing logic after initialization
9. Ready for UseBean is now fully initialized and ready for use
10. DestructionWhen container shuts down, bean is destroyed via @PreDestroy / destroy() or DisposableBean

🧩 Lifecycle Hooks and Interfaces

Hook TypeInterface / AnnotationPurpose
AwarenessBeanNameAware, BeanFactoryAware, ApplicationContextAwareTo get reference to container resources
Init Phase@PostConstruct, InitializingBean, custom init-methodCustom setup logic
Post ProcessingBeanPostProcessorModify bean before and after initialization
Destroy Phase@PreDestroy, DisposableBean, custom destroy-methodCleanup logic

💡 Detailed Example

Let's walk through an actual Spring Boot example that shows all lifecycle phases:

java
@Component
public class MyBean implements BeanNameAware, BeanFactoryAware, 
                             ApplicationContextAware, InitializingBean, DisposableBean {

    public MyBean() {
        System.out.println("1. Constructor: Bean is being instantiated");
    }

    @Override
    public void setBeanName(String name) {
        System.out.println("2. BeanNameAware: Bean name is " + name);
    }

    @Override
    public void setBeanFactory(BeanFactory beanFactory) {
        System.out.println("3. BeanFactoryAware: BeanFactory is set");
    }

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        System.out.println("4. ApplicationContextAware: ApplicationContext is set");
    }

    @PostConstruct
    public void postConstruct() {
        System.out.println("5. @PostConstruct: Custom init method");
    }

    @Override
    public void afterPropertiesSet() throws Exception {
        System.out.println("6. InitializingBean: afterPropertiesSet called");
    }

    @PreDestroy
    public void preDestroy() {
        System.out.println("7. @PreDestroy: cleanup before bean destroy");
    }

    @Override
    public void destroy() throws Exception {
        System.out.println("8. DisposableBean: destroy called");
    }
}

🔁 BeanPostProcessor Example

To hook into before and after initialization:

java
@Component
public class MyBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
        if (bean instanceof MyBean) {
            System.out.println(">> BeanPostProcessor - Before Initialization of: " + beanName);
        }
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
        if (bean instanceof MyBean) {
            System.out.println(">> BeanPostProcessor - After Initialization of: " + beanName);
        }
        return bean;
    }
}

📌 Best Practices (Market Standards)

✅ Use @PostConstruct and @PreDestroy

  • Preferred over InitializingBean / DisposableBean for clean POJO-style coding

  • They are JSR-250 compliant and don't tie your code to Spring interfaces

✅ Avoid ApplicationContextAware (If possible)

  • It leads to tight coupling between your beans and Spring container

  • Consider constructor injection instead

✅ Use @Component with constructor injection

  • Cleaner and more testable code

✅ For External Configuration, Use @ConfigurationProperties

  • Instead of injecting with @Value, prefer binding configs to a POJO

✅ For Complex Post-processing, Use BeanPostProcessor

  • Good for cross-cutting concerns like logging, metrics, proxies

✅ Manage Bean Scope Appropriately

  • Use Singleton for shared beans (default)

  • Use Prototype for per-invocation stateful beans

🔐 Real-world Use Case: Managing Connections

java
@Component
public class DBConnection {

    private Connection conn;

    @PostConstruct
    public void init() {
        // connect to DB
    }

    @PreDestroy
    public void close() {
        // close DB connection
    }
}

This ensures that connections are opened/closed at appropriate times in bean lifecycle.

🧪 Testing Strategy

  • Use Spring Boot Test with @SpringBootTest

  • Mock lifecycle components using @MockBean

  • Manually validate lifecycle logs in integration tests

🧠 What is Dependency Injection?

Dependency Injection (DI) is a design pattern where an object’s dependencies are provided from the outside rather than the object creating them itself.

In simpler terms:

"Don’t ask for your dependencies — have them delivered."

✅ Why Dependency Injection?

  • Loose coupling between classes

  • Easier testing (mocking dependencies)

  • Better modularization and reuse

  • Configuration flexibility (XML, annotations, Java config)

🧰 How Does Dependency Injection Work Internally in Spring?

Spring uses an Inversion of Control (IoC) container to manage object creation and wiring.

Here's a simplified breakdown:

  1. Spring Context Starts

    • Loads beans defined via annotations (@Component, @Bean) or XML.

  2. Bean Definitions Are Scanned

    • Spring identifies which classes are beans.

  3. Dependency Graph Is Built

    • Spring checks which beans depend on other beans.

  4. Dependencies Are Resolved

    • Based on constructor, field, or setter, Spring injects dependencies.

  5. Beans Are Instantiated and Wired

    • Beans are created in the proper order and wired accordingly.

  6. ApplicationContext Keeps Bean Registry

    • Beans can now be reused and retrieved from the Spring context.

🧩 Components of Spring DI

@Component, @Service, @Repository, @ControllerMarks classes as Spring-managed beans
@AutowiredTells Spring to inject the dependency
@QualifierSpecifies which bean to inject if multiple candidates

🧪 Types of Dependency Injection in Spring

Spring supports 3 types:

TypeDescriptionUse Case
1. Constructor InjectionDependencies are injected via constructorMandatory dependencies, immutability
2. Setter InjectionDependencies are injected via setter methodsOptional or configurable dependencies
3. Field InjectionDependencies are injected directly into fieldsLess boilerplate, but harder to test

1️⃣ Constructor Injection (Recommended)

java
@Component
public class OrderService {

    private final PaymentService paymentService;

    @Autowired
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

✅ Pros:

  • Immutable dependencies

  • Easier to test (can use constructors in unit tests)

  • Better for mandatory dependencies

🚫 Cons:

  • Boilerplate for many dependencies

2️⃣ Setter Injection

java
@Component
public class OrderService {

    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

✅ Pros:

  • Good for optional/configurable properties

🚫 Cons:

  • Allows the object to be in an incomplete state

3️⃣ Field Injection

java
@Component
public class OrderService {

    @Autowired
    private PaymentService paymentService;
}

✅ Pros:

  • Very concise

🚫 Cons:

  • Harder to unit test (can’t mock easily)

  • Encourages hidden dependencies

✅ Best Practices & Market Standards

🔹 1. Use Constructor Injection (Always Preferable)

  • Promotes immutability

  • Mandatory dependencies are clear

  • Works great with final fields

🔹 2. Avoid Field Injection

  • Makes unit testing harder

  • Hidden dependencies — bad for design clarity

🔹 3. Use @Qualifier for Multiple Beans

  • Avoids NoUniqueBeanDefinitionException

java
@Autowired
@Qualifier("paypalService")
private PaymentService paymentService;

🔹 4. Don’t Overuse @Autowired

  • Let Spring resolve beans by constructor injection

  • Avoid unnecessary autowiring of everything

🔹 5. Split Configuration Using @Configuration Classes

java
@Configuration
public class AppConfig {
    @Bean
    public PaymentService paymentService() {
        return new PaypalService();
    }
}

🔹 6. Leverage @Primary for Default Bean

java
@Primary
@Component
public class DefaultPaymentService implements PaymentService {}

🔹 7. Use Profiles for Environment-based Beans

java
@Profile("dev")
@Component
public class DevDataSourceConfig {}

@Profile("prod")
@Component
public class ProdDataSourceConfig {}

🔹 8. Avoid Circular Dependencies

  • Constructor-based DI can help detect circular dependencies at startup
